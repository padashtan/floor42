# ADR-0044: Sessions and script tokens in memory, the exact Origin, and what an agent of the same user still reaches

Date: 2026-10-31 · Status: Accepted · Amends ADR-0007 and ADR-0034

## Context
A read-only review found claims stronger than the evidence:
- **Origin.** `LocalAccessGuard` accepted any loopback Origin, whatever its port. SameSite does not tell ports apart: a page on `http://127.0.0.1:8000` (a server an agent starts in its worktree, a dev server) is the same site as the daemon, so the browser sends the director's `SameSite=Strict` cookie with its requests. Such a page could `POST /api/agents/{id}/resume` with a plain `no-cors` fetch and open `/ws/events`. A missing Origin was accepted everywhere.
- **CSP.** ADR-0007 promised a strict Content-Security-Policy. Only deliverables and replay exports had one; the application page had none.
- **Docker.** ADR-0034 said the sign-in link printed on the container's output is read by the host "and processes inside the container do not". Agents run as uid 1000, the daemon's own uid, and the daemon is PID 1: nothing had been checked.
- **Sessions.** Browser sessions had no expiry, no list and no sign-out. Scripts had only the director's own token, in a file (`floor42.director-token-file`) any unconfined agent can read.
- **Remote use.** Nothing said how to use a daemon on another machine; a reverse proxy would have been half-trusted.

## Options

| | B. `http://` + the request's own Host, exactly; other origins only from `floor42.access.extra-origins`, set in `%dev` only | Vite's own port must be listed in dev mode | **Chosen.** Docker publishing another host port still works: the browser's Host and Origin agree |
| | C. Compare with the port the daemon listens on | Breaks `FLOOR42_PORT` in Docker and SSH tunnels on another local port | Rejected |
| CSRF beyond Origin | D. Origin only | A browser bug or extension that strips Origin opens the door | Rejected alone |
| | E. | Script tokens | F. Keep the director's token in a file | Re-opens D12 | Deprecated: still works, with a warning |
| | G. Tokens rebuilt at start from the hashes in the journal | Survive restarts | Rejected: `[fake:forge]` proves an agent of the same user can open the journal for writing; it could append an `ApiTokenIssued` with a hash of its own and be the director after the next restart |
| | H. Tokens in the daemon's memory only, issued from the desk, shown once, scoped, ≤ 30 days; the journal keeps their SHA-256 as a record, never used to authenticate | A restart signs scripts out: issue a new token | **Chosen** |

| | J. Make the daemon non-dumpable (`prctl(PR_SET_DUMPABLE, 0)`, FFM, Linux) | `jcmd` and debuggers cannot attach (`floor42.process.non-dumpable=false` turns it off) | **Chosen**: closes `/proc/<daemon>/fd`, `environ` and `mem` to the same uid |

## Decision
- **Origin.** `LocalAccessGuard` refuses an Origin that is not `http://` + Host (case-insensitive) or listed in `floor42.access.extra-origins` (`%dev`: Vite's 5173 and the dev launcher's 7421). It applies to every path, `/auth/open` included.
- **Browser requests.** A request authenticated by the session cookie must name its Origin when its method changes something (anything but GET, HEAD, OPTIONS) or when it opens a `/ws/` socket, and must carry `X-Floor42-Request: 1` when it changes something. The web client sends the header on every call (`REQUEST_HEADER` in `api/client.ts`); Swagger UI's "Try it out" too (`quarkus.swagger-ui.request-interceptor`). Bearer requests (scripts) need neither; a foreign Origin is still refused for them.
- **Proxies.** A request carrying `X-Forwarded-For`, `X-Forwarded-Host` or `Forwarded` is refused (403 `FORWARDED`, pointing at docs/remote.md). The supported way to a remote daemon is an SSH tunnel with `FLOOR42_SIGN_IN_DELIVERY=stdout`.
- **CSP.** Every HTML page outside `/api` and `/q/` gets, unless it already has a policy: `default-src 'self'; script-src 'self'; style-src 'self'; style-src-elem 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; connect-src 'self' ws://<host>; worker-src 'self' blob:; frame-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'none'; form-action 'self'`, plus `X-Frame-Options: DENY`. Every answer gets `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. The one inline exception is `<style>` elements: xterm.js 6's DOM renderer creates them with computed sizes and colours, which no hash can match, and it has no nonce option. Inline style attributes and every inline script stay refused. The Vite build has no inline script and no eval. The deliverables' PDF viewer moved from `<object>` to an `<iframe>`; deliverables keep their own sandbox policy. Swagger UI under `/q/` keeps Quarkus's page, which needs inline scripts.
- **Sessions** (`SessionRegistry`, in memory). Each has an id, a kind (`BROWSER` or `SCRIPT`), a scope, when it was created and last used, its user agent, and the SHA-256 of its secret; the secret itself is never kept. A browser session ends 8 h unused or 24 h after sign-in (`floor42.sessions.idle-hours`, `absolute-hours`). `POST /auth` with the director's token as a bearer opens a browser session (the token never sits in the cookie store); `GET /auth?token=` is refused (`TOKEN_IN_URL`), a full-scope token does not belong in a URL, the browser history or a log. Routes: `GET /api/auth/sessions`, `DELETE /api/auth/sessions/{id}`, `POST /api/auth/sign-out` (clears the cookie), `POST /api/auth/sign-out-everywhere` (empties the registry and replaces the director's token).
- **Script tokens.** `POST /api/auth/tokens {scope, days, label}` issues one, `read` | `missions:write` | `all`, 1 to 30 days, the value in that answer only. The journal records `ApiTokenIssued` and `ApiTokenRevoked` (Origin REAL, actor DIRECTOR) with the token's id and SHA-256, never its value. The guard enforces the scope: `read` gets 403 `SCOPE` on anything that changes something; `missions:write` (narrowed in 1.8.0) may change only what creates and steers a mission: `POST /api/missions`, `/api/missions/{id}/approve`, `/reject`, `/tickets/approve`, `/workshop/directive`, `/nudge`, and `/api/questions/{id}/answer` for the mission's own questions; the desk refuses it a permission question (`ACTION_APPROVAL`, 403 `SCOPE`), which only the desk can tell from the others. The director's files, the workshop's acceptance and file edits, pull requests, budgets, checks, tool permissions, cancel/complete/resume, committees and remembered approvals (`/forget`) need `all`; `all` is the director. Quarkus's pages under `/q/` (OpenAPI, Swagger UI) need the director too, by cookie or bearer of any scope; only dev mode opens them (`floor42.access.open-quarkus-pages`). Tokens die with the daemon. A token the journal failed to record is revoked at once.
- **The token file** (`floor42.director-token-file`) keeps working, with a deprecation warning naming the replacement.
- **The daemon is non-dumpable on Linux** (`ProcessHardening`, at start).

## What is proven (tests, and a container run on 2026-10-31)
- A page on another port of 127.0.0.1 or localhost gets 403 with the cookie, on a POST and a GET. A cookie POST without Origin, or without the header, gets 403. A bearer POST needs neither. `/ws/events` opens with the cookie and the daemon's own Origin, and refuses a foreign Origin (403) and a missing one (403). `/auth/open` refuses a foreign port. `BrowserRequestsTest`; in Chrome, `security.e2e.ts` "a page on another local port cannot drive the daemon…" (the attacker's POST and WebSocket leave nothing behind).
- The page's policy, and no CSP violation on any browser journey, the terminal's xterm included. `BrowserRequestsTest.thePageCarriesAStrictPolicyAndTheApiNoSniff`; the e2e fixture fails a journey on any `securitypolicyviolation`.
- Scopes per route class: `SessionsApiTest.aMissionsTokenCreatesApprovesAndDirectsMissions`, `aMissionsTokenGets403OnFilesAcceptancePullRequestsAndPermissions`, `aMissionsTokenAnswersAMissionsQuestionButNotAPermission`; the documentation behind the director: `BrowserRequestsTest.theApiDocumentationNeedsTheDirector`, and in Chrome the top bar's Docs link still renders Swagger UI (`panels.e2e.ts`).
- Sessions and tokens: `SessionRegistryTest` (8 h idle, 24 h absolute, ≤ 30 days, hash only); `SessionsApiTest` (scopes, hash in the journal and the value in no file of the data directory, the hash opening nothing, revoke, sign-out, sign-out everywhere replacing the director's token). `ClaudeCodeRuntimeTest.anAgentsShellFindsNoUsableDirectorCredential` still finds nothing usable while a live script token's hash sits in the journal.
- Forwarded requests: `BrowserRequestsTest.aRequestAProxyForwardedIsRefusedWithAClearError`.
- **Same OS user.** `ClaudeCodeRuntimeTest.anAgentsShellRunningAsTheDaemonsUserCanWriteTheJournalAndReadCredentials` (`[fake:forge]`, permission checks only, on the test's journal and a planted credentials file) shows an agent's shell **can** open the journal for writing and **can** read Claude Code's credentials. The run on Windows with the director's own user shows the same.
- **In the container** (`docker build` of this branch, Docker Engine 29.9.2 in WSL Debian, checks run as uid 1000 beside PID 1 `java`, also uid 1000): with `FLOOR42_PROCESS_NON_DUMPABLE=false`, which is the behaviour before this change, `/proc/1/fd/1`, the daemon's standard output carrying the sign-in link, and `/proc/1/environ` **were reachable**. ADR-0034's sentence was false. With the default, both are refused (`ls /proc/1/fd`: Permission denied). The journal is writable by uid 1000 in both cases.

## What it does not stop
- **An agent of the same user can still write the journal**, on Windows without the sandbox, on Linux, and in Docker. A forged row takes effect at the next start, as any event would. Script tokens are not rebuilt from it, so a forged `ApiTokenIssued` grants nothing. A forged permission or approval would, though. Debt D16.
- **Claude Code's credentials** (`~/.claude/.credentials.json`) are readable by every agent: they are Claude Code processes and need them. The container keeps them away from the rest of your machine, not from the agents.
- Everything ADR-0034 lists for a same-user process outside Docker: other processes' memory (Windows), the browser's cookie store, the screen and keyboard.
- `missions:write` no longer approves a tool call (1.8.0), but it still answers a plan-limit, budget or staffing question, which can spend money: a token of that scope is a director's delegate for missions, not a read-only bot.

## Consequences
- Scripts use a script token from the desk (System > Sessions and tokens); after a restart, issue a new one. `floor42 "objective"` (`bin/floor42`, `bin/floor42.ps1`) reads a `missions:write` token from `FLOOR42_TOKEN`, else the deprecated file with a warning.
- A page of the director's own must send `X-Floor42-Request: 1`; a new `fetch` outside `api/client.ts` must too.
- Running Floor42 behind a proxy no longer half-works: it is refused, by design.

## Reopen if
Agents can run under their own OS account (the director's repositories group-writable, or a helper with the right to switch uid); a second user or a remote client needs real authentication (ADR-0007); xterm.js offers a nonce or constructable stylesheets, which would let `style-src-elem` drop `'unsafe-inline'`.

## Amendment 2026-11-01: what the daemon reads at its next start (1.8.0)

**Context.** A design review of 1.7.0 asked what an agent running as the daemon's own OS user can change in what the daemon does at its next start, given that it can stop the daemon (`kill -TERM 1` in Docker, where `restart: unless-stopped` starts it again). Checked in a container built from the 1.7.0 release (Docker Engine 29.9.2, WSL Debian, every step as uid 1000):
- `restore-pending.properties` written in the data folder rolled the journal back at the next start (ADR-0042's restore had no proof of who prepared it);
- `.env` or `config/application.properties` in the working directory `/home/office`, both read by Quarkus in prod, set `FLOOR42_PROCESS_NON_DUMPABLE=false`: the restarted daemon was dumpable again. A JDBC URL could as well have turned SQLite's `enable_load_extension` on;
- `/opt/floor42` belonged to uid 1000: the jar and `lib/main` were writable.

**Options for the restore.** (a) Keep a marker file but sign it: the key must outlive the restart, so it sits on a disk the same user reads. Rejected. (b) Re-confirm the restore after the restart: the restored journal would then have to be swapped live, which ADR-0042 refused. (c) Keep the restore in memory and apply it during the daemon's own orderly stop, through SQLite's online backup API on a pool connection: no file asks for it, so nothing can be forged; the cost is that a crash forgets it. Chosen.

**Decision.**
- A restore is prepared only by the director's API (`PUT /api/backups/restore`), held in memory, and applied by the last `ShutdownEvent` observer: the journal then takes no more appends, copies itself as `before-restore-*`, and is rewritten in place. A start never restores. A `restore-pending.properties` found at start is moved to `restore-pending.refused.properties`, logged as an error and shown in the red journal banner (`GET /api/journal/alerts`). The stop writes `restore-outcome.properties` for the next start to report. It is information only, and is checked against the journal's events and the kept copy (`verified`).
- `ConfigGuard` refuses the start when Quarkus read configuration from `.env` or `config/` in the working directory, when the journal's URL is not exactly `jdbc:sqlite:<data-dir>/floor42.db?transaction_mode=IMMEDIATE`, or when any datasource property adds driver properties or names `load_extension`. The journal also asks its own connection to load an extension and requires "not authorized". The environment and `-D` stay the director's: an agent cannot change those of a running daemon or of the container.
- The image runs the daemon from `/opt/floor42`, root-owned (directories 0755, files 0644); only the `office-home` volume is writable by uid 1000. `bin/floor42-docker login` runs `claude` with `-u 1000 -e HOME=/home/office -w /home/office`.
- `ProcessHardening` reads the flag back after setting it (an error if it did not take) and `/api/status` reports `process.nonDumpable` as the kernel answers it at each request.
- The journal's transactions begin `IMMEDIATE`. Another program holding the journal makes an append fail after SQLite's busy timeout with `JOURNAL_LOCKED` and a banner. It is not prevented.

**Proven.** `BackupStoreTest.aRestoreMarkerPlantedInTheDataFolderIsRefusedAtStartAndReported`, `…aRestoreTheDirectorPreparedIsAppliedWhenTheDaemonStopsAndReportedByTheNextStart`, `…aForgedOutcomeIsReportedAsNotVerified`, `PlantedRestoreMarkerTest`, `ConfigGuardTest`, `SqliteJournalTest.theJournalsConnectionsBeginImmediateAndRefuseExtensions`, `StatusResourceTest.reportsWhetherTheDaemonIsNonDumpableAsTheKernelSaysIt`, `JournalLockTest`. In the 1.8.0 image, the three checks above fail for the agent, a container forced to run from `/home/office` with a planted `.env` exits with "Floor42 refuses to start", and a restore prepared from Settings is applied by `docker restart` and reported verified (docs/docker.md).

**Not stopped.** The journal itself stays writable by the same user (D16). Without Docker or the WSL sandbox, the installed copy in `~/.floor42/app` and the launchers are the user's own files: a same-user process can replace them (SECURITY.md).

## Amendment 2026-11-01 (2): counter-check of the first amendment

An independent counter-check of the first amendment's image found more, each shown in a container as uid 1000:
- **The JVM's attach mechanism was open.** `touch /tmp/.attach_pid1; kill -QUIT 1` made the daemon create `/tmp/.java_pid1`. With `java.instrument` present, any same-uid process could load an agent into the daemon. Non-dumpable does not cover attach.
- **Rollback by swapping the file.** `mv -f` of an older copy over `floor42.db`, then `kill -TERM 1`: the next start replayed 35 events instead of 67, silently. The first amendment's line "a restore at the next start: no" was true of the marker only.
- **The restore outcome file was shown as verified** when it said "not applied", with a text of the forger's.
- **The prepared copy could be swapped** between the director's click and the stop.
- `migrated-from-office.properties` was read again on every call and decides which folders are guarded.

**Decision.**
- Every launcher starts the JVM with `-XX:+DisableAttachMechanism`: the image's entry point, `bin/floor42`, `bin/floor42.ps1`, the tests' `argLine`, and the dev launchers (`FLOOR42_DEV_ATTACH=1` opts out, for `jcmd` or a profiler; dev mode was checked to start with it). `/api/status` reports `process.attachDisabled` from `HotSpotDiagnosticMXBean`. A banner shows on Linux when it is off. On Windows it closes the JVM's own attach only; a same-user process can still read the daemon's memory (SECURITY.md).
- **Journal continuity, detected, not prevented.** `journal-continuity.properties` holds the event count, the last sequence and a SHA-256 of the last row. It is written at start, at most every 30 s after appends, and at the stop, from the live connection. A start that finds fewer events (`SHORTER`) or the last row seen missing or different (`DIVERGED`) raises `continuity` in `GET /api/journal/alerts`, a red banner and an error log. The record is then held, so every start reports it again, until the director acknowledges (`POST /api/journal/alerts/continuity/acknowledge`).
  - The stop compares the journal's file identity (its inode, Linux) with the one opened at start. When another file took its name, it copies what its connections still read as `displaced-<time>.db`, never rotated, so the real journal survives. A prepared restore is then not applied.
  - **Writes are not refused.** Option considered: stop appending until the director acknowledges. Rejected. The record is a file the same user can rewrite, so refusing writes proves nothing against a forger: one who rewrites the record together with the journal is never refused, and only the honest case (the director's own copy put back by hand) would be stopped. Refusing would not give an agent a new way to freeze the office either: a lock held on `floor42.db` already does that (`JOURNAL_LOCKED`, SECURITY.md). The cost of not refusing: events written before the director reads the banner go into the rolled-back journal. The `displaced-*` copy keeps the other side. *(Argument corrected by amendment 3: it first read "refusing would give any agent a one-line way to freeze the office".)*
- **Restore outcome:** `verified` becomes `matchesJournal`. It is true or false for a restore reported done, and null for one reported not applied, which has nothing to check. The UI always says "a file the last stop left reports …". Its text is bounded (200 characters, no control characters).
- **Prepared copy:** its SHA-256 is taken at preparation. The stop copies it to a private temporary file, checks that file's hash, then checks and restores that file. *(Superseded by amendment 3: the copy is read once into memory and no file stands between the check and the restore.)*
- `DataFolders` reads the migration record once at start (`freeze`). Only the daemon's own `recordMigration` updates it later.
- `ConfigGuard` logs and shows (`configFiles`) any configuration file read from outside the daemon's own files, for instance one named by `QUARKUS_CONFIG_LOCATIONS`. Such a file is not refused: the environment is the director's.

**Proven.** In order: `StatusResourceTest.reportsWhetherTheDaemonIsNonDumpableAsTheKernelSaysIt` (`attachDisabled`), `BackupStoreTest.aJournalShorterThanTheLastRunSawIsReportedUntilAcknowledged`, `…aJournalWhoseLastSeenRowChangedIsReportedAsDiverged`, `…aForgedFailedOutcomeClaimsNothingCheckedAndItsTextIsBounded`, `…aBackupChangedAfterTheDirectorPreparedItIsRefusedAtTheStop`, `DataMigrationTest.theMigrationRecordIsReadOnceAtStart`, `ConfigGuardTest.aConfigurationFileOutsideTheDaemonsOwnFilesIsReported`, `JournalApiTest`. In the rebuilt image:
- no attach socket is created;
- the swap gives the `SHORTER` banner and a `displaced-*` copy holding the 67 events;
- the forged outcome shows `matchesJournal: null`;
- the swapped copy is refused at the stop;
- `QUARKUS_CONFIG_LOCATIONS` into the volume is logged.

**Not stopped.** An agent that rewrites both the journal and the continuity record (D16). Memory reads on Windows.

## Amendment 2026-11-01 (3): counter-check of the second amendment

A counter-check of amendment 2 found:
- **Idleness defeated the continuity check.** After a file was moved over `floor42.db`, Agroal closed the idle connections after about five minutes; the next one opened the forged file. Every measure went through the pool, so the stop kept the forged file as `displaced-*`, rewrote the record from it (0 events), and the next start showed nothing. The real journal survived only in a rotating `startup-*` copy.
- **A missing or unreadable record raised nothing.** It was taken for a fresh data folder.
- **The prepared copy went through the shared temporary folder.** The stop copied it to `/tmp`, hashed that file, then restored it by its name: a same-user process could change it in between.
- The argument against refusing writes was wrong (a lock on `floor42.db` already freezes the office; see above).
- The Docker image could not be tied to its commit: its build has no `.git`, so `/api/status` said `build.commit: null`.

**Decision.**
- **An anchor.** At start the daemon opens a read-only connection on the journal, outside the pool, and holds it until its stop (`ContinuityKeeper`). The record is measured through it, the `displaced-*` copy is taken through it, and the file's identity (inode) is compared with the one it opened before each record and at the stop. On Linux an open connection keeps reading the file it opened whatever takes the name, so the record follows the journal this daemon opened, never the forged one.
- **The record is never rewritten from a journal that does not continue the last one written.** If the journal stops continuing it while the daemon runs (a rewrite in place), the break is held and shown at once, as at a start. Two exceptions start a new line: a restore the director prepared, and their acknowledgement.
- **`MISSING` and `UNREADABLE`.** No record beside a journal holding events, or a record that cannot be read, raise the same banner (`continuity.reason`, `origin: REAL`), held until the director acknowledges. A journal with no event and no record is a fresh data folder: nothing is said. The first start of 1.8.0 on an existing journal showed `MISSING` once, in the alarm's red; amendment 3 below gives that case its own presentation.
- **The restore reads the copy once, into memory.** Those bytes are hashed against the preparation's SHA-256, deserialized into an in-memory SQLite database, checked (`quick_check`, events counted) and written into the journal through SQLite's online backup API. No file stands between the check and the restore. A copy above 1 GiB is not restored this way (restore it by hand, daemon stopped, docs/backups.md); amendment 3 also bounds it by the heap.
- **The image carries its commit.** The Dockerfile takes `FLOOR42_COMMIT`, `FLOOR42_COMMIT_TIME` and `FLOOR42_COMMIT_DIRTY` as build arguments and writes `build-commit.properties` with `bin/build-commit-properties`; `make docker-build`, `bin/floor42-docker` and the release workflow pass them. A missing or malformed commit writes nothing (null, never a guess).

**Proven.** `JournalContinuityTest.aSwapFollowedByConnectionsReopenedOnTheForgedFileIsStillCaught` (every new connection opens the forged file, the name has another identity: failed before, with the record at 1 event), `…onLinuxAJournalMovedOverTheFileIsCaughtThroughItsInode` (a real `rename` over the file, real inodes; Linux only), `…aJournalRewrittenInPlaceWhileTheDaemonRunsIsReportedAndNotRecorded`, `…aMissingRecordBesideAJournalWithEventsIsReportedAndAFreshFolderIsNot`, `…anUnreadableRecordIsReported`, `BackupStoreTest.aCopyChangedBetweenItsHashAndTheRestoreChangesNothingRestored` (the copy and the backup overwritten between the hash and the restore: before, the tampered copy was restored, and the outcome said "left as it was"), `BuildCommitPropertiesTest`. An image built with the build arguments answered `/api/status` with its commit (`dirty: false`). The swap followed by five idle minutes was not re-run in a container.

**Counter-check of this amendment, and its fixes.**
- **The memory budget.** A copy under 1 GiB but larger than the heap (300 MB with `-Xmx128m`) threw `OutOfMemoryError` at the stop, which was caught nowhere: no outcome, no `lastRestore`, and nothing told the director the restore had not happened. Now a copy is restorable only if it weighs at most a quarter of `Runtime.maxMemory()` (the bytes, then SQLite's deserialized copy, about twice the size, plus the daemon's own needs; `floor42.backup.restore-memory-bytes` overrides it, tests use a tiny one), and never more than 1 GiB. It is refused when prepared (`BACKUP_UNREADABLE` with the reason; the Settings button is disabled with the limit, EN and FR) and checked again at the stop. Any failure at the stop writes the outcome "not applied": `OutOfMemoryError` is caught narrowly around the restore alone, with a written reason, and a stop that cannot open the journal or finds the file replaced writes one too (`JournalBackups.notApplied`). Proven by `BackupStoreTest.aCopyHeavierThanTheMemoryBudgetIsRefusedWhenPreparedAndAgainAtTheStop` and `…anOutOfMemoryErrorWhileRestoringIsAnOutcomeNotAnEscapedError` (failed before: the error escaped, no outcome).
- **The first start of 1.8.0 looked like a rollback alarm.** Every upgrade showed the red `MISSING` banner once, teaching the director to dismiss it. Detection stays honest: a missing record is still held until acknowledged, and nothing trusts a marker to excuse it. Only the presentation changes. Migration V2 adds `continuity_epoch(checked)`, 0 until a check ends without a break (or the director acknowledges the notice). `MISSING` with `checked = 0` is reported as `FIRST_CHECK`: an amber notice saying the check starts now, to be acknowledged. Every other `MISSING` (and a missing or unreadable table) stays the red alarm. **What a forger could do with it:** whoever can rewrite the journal (the same OS user, D16) can set `checked = 0`, or restore a copy made before 1.8.0, and delete the record: the director then sees an amber notice instead of a red one, once, still held until acknowledged. The cheapest path is two file operations: copy a backup taken before 1.8.0 over `floor42.db` and delete `journal-continuity.properties`. Note too that the hourly copies taken while a `FIRST_CHECK` notice is unacknowledged carry `checked = 0`: restoring one of them later gives the amber notice again. That forger could equally have rewritten the record itself, which is already not stopped; the notice only softens the colour and the wording, and its text says that without an upgrade it is an alarm. Rejected: a marker file in the data folder (forgeable and no better), a version column on events (a format change for a hint).
- **`UNREADABLE` has its own log text**, no longer the first-start explanation of `MISSING`.
- **A check that could not be made is a banner.** When the anchor cannot be opened, the reason `ANCHOR_FAILED` (origin REAL) says that nothing is detected this run; acknowledging clears it for this run.

**Not stopped.** An agent that rewrites both the journal and the record, between two runs (D16). On Linux, the five idle minutes are no longer the issue, but a same-user process can still write the file the anchor holds, in place: that is seen at the next record, not prevented.
