# ADR-0021: Company settings in the journal, the screen's language in the browser

Date: 2026-10-21 · Status: Accepted. The director asked for every screen text in French, chosen in a settings panel, and lifted the "UI in English" rule; English stays available.

## Context
Two kinds of choice were mixed up in a "settings" request:
- choices about **the company**: how many sessions run at once (ADR-0019), the plan-limit threshold (ADR-0016), the retrospective model (ADR-0020), the language agents write in. They change what agents do and what they cost, so they are director's decisions, and Office keeps every decision in the journal;
- the **language of one screen**: it changes nothing agents do. Journaling it would make one viewer's preference a company fact.

Until now the company choices were daemon configuration keys, read once at startup.

## Decision
- **Company settings** are a closed list (`Setting` in the domain), each with the values it accepts. The director changes one with `PUT /api/settings/{key}`; Office records `SettingChanged` (a null value goes back to the daemon's default). `OfficeSettings` reads the value in force each time it is needed: the director's choice, else the configuration key, so a change applies from the next session on, without a restart. Setting the value already in force records nothing.
- **The agents' language** is one of those settings. Briefs ask for prose in that language and keep the marker lines Office parses (`VERDICT`, `LESSON`…) in English: they are read by code, not by a person.
- **The screen's language** is chosen per viewer in the settings panel and kept in that browser only (`localStorage`, with the browser's language as the first guess). It never reaches the server.
- **What is translated.** The UI's own texts go through two typed catalogues (`office-web/src/i18n/en.ts`, `fr.ts`); a key missing from one fails the type check. What agents and commands wrote is shown as recorded, in its own language.

## Consequences
- The settings panel shows each company setting with its default and whether the director changed it; each change appears in the event log as the director's decision.
- Translation comes in lots. Lots 1 and 2 cover every text the UI writes itself. Fixed words the server sends (statuses, verdicts, answer options, scorecard labels) are translated by the UI with the server's own text as fallback; only the label changes, the option sent back to the server stays its own. The sentences the server composes (event lines, questions, profile facts, the night's reason, retrospective facts) come in lot 3, as message codes with parameters that the UI translates. Until then they stay in English, even on a French screen.
- Lot 3, first part (2026-10-30): event log lines. Each event view carries a `code` (the event type, plus a variant where the sentence changes, such as `AgentSessionEnded.failed.cost`) and `params` (the event's fields as text, without outputs, deliverables or findings, plus a few values Office computes: who works a ticket, which call an action is, a cost written once). The UI writes the line from `ev.<code>` in its catalogue and falls back to the server's English `text` for a code it does not know. Fixed words inside a line (verdicts, criticality, roles) use the existing word keys. The short activity line above an agent in the scene uses the same translated line, handed in by the UI (the scene does not know the catalogues).
- Amendment (2026-11-01): the event view no longer carries the English `text`. Its only readers were the UI's fallback for an unknown code and the replay file; the server's `EventCatalogueContractTest` now lists every code it can emit (`floor42-web/src/i18n/event-codes.json`) and the UI's `catalogue.test.ts` fails when en.ts or fr.ts lacks one or uses a placeholder the server does not fill. The replay file, read without a screen, gets its lines from the English catalogue on the server (`EnglishLines`, from `event-lines.en.json` extracted from en.ts). Each event's params are built explicitly by the renderer of its area: renaming a field breaks the build, not a placeholder.
- Lot 3, second part (2026-10-30): questions. `QuestionAsked` records a `Phrase` (code and values) beside the English subject and context it wrote; the question view exposes it as `phraseCode` and `phraseParams`, and the UI writes `q.<code>.subject` and `q.<code>.context` when its catalogue has them. Older journal events have no phrase and show as recorded; an agent's own question has none either. Parts made of free text (a reviewer's findings, an error message, the committee's recommendation, the plan-limit estimate, the approval's coverage) stay as recorded. - Lot 3, third part (2026-10-30): profile facts, scorecard values and the night's reason carry a code (and values) beside their English text; the UI writes `fact.*`, `scorev.*` and `night.*`. Lists of data inside a value (the last verdict of each ticket) stay as recorded.
- Deliberately left as recorded: the retrospective facts. They are the brief Office gave the participants, in the language the agents work in; showing them otherwise would misstate what the agents read.
- No translation library: a small typed function (`t`, `tr`) is enough for two languages and keeps the build free of a runtime dependency.
