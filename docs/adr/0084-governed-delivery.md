# ADR-0084: Governed delivery: the checks of the exact commit, a merge on the proven click

Date: 2026-11-17 · Status: Accepted (1.4.0)

## Context
ADR-0036 lets the director open a pull request from Floor42 and read its checks with `gh pr checks`. Two gaps remain before a delivery can be called governed. First, `gh pr checks --json` has no commit field: it answers for the head of the pull request at the time of the call, so a push between the call and the screen leaves checks of an older commit on display and nothing says so (measured on PR 9 of `padashtan/floor42`: 12 checks, none with a sha). Second, the merge happens outside Floor42, on GitHub's page, with no trace in the journal and no link to the checks that justified it.

## Options
| Option | What it costs | Verdict |
|---|---|---|
| A. Keep `gh pr checks`, record the PR's `headRefOid` before and compare after | Two extra gh calls; the checks are still the CLI's folded view (`state`/`bucket`), and the CLI hides a superseded run in a way gh does not document | Rejected as the only source: it binds an answer to a commit by comparison, not by the query |
| B. Read the check runs and the statuses of the commit: `gh api repos/{o}/{r}/commits/{sha}/check-runs` and `.../status`, with the head read before and after | The query itself names the commit (`head_sha` on each run); Floor42 folds `status`/`conclusion` into the CLI's buckets and picks the latest run per name; no paging (a commit with over 100 runs is refused) | **Taken** |
| C. Only the legacy combined status (`commits/{sha}/status`) | Returned `pending` with 0 statuses on the same repository: a guard on its combined state would wait forever | Rejected as the source; its individual statuses are read next to the runs |
| D. Floor42 merges with a stored token or an agent's tool | A credential Floor42 holds, or an agent acting on GitHub (ADR-0036 option A and D) | Rejected |
| E. The director's own gh, on a click that proves the director | One more act at the strong level; nothing stored | **Taken** |

## Decision
- **Evidence of a commit.** `POST /api/missions/{id}/pull-requests/{n}/checks` reads the head sha (`gh pr view --json headRefOid`), the check runs of that sha, then the head again. A head that moved in between is refused (409 `HEAD_MOVED`) and nothing is recorded. A check is a check suite (one workflow) and a name: within that key the run with the highest id wins, so a cancelled run superseded on the same commit is not a failure of the commit, while the same name in two workflows stays two checks (the name then carries `(suite <id>)`) and one failing is not hidden by the other. A run still cancelled with nothing after it counts as failed. The legacy statuses of the commit count one by one (`success` pass, `pending` pending, anything else fail); the combined state, pending with no status reported, is never read. Buckets: `success` is `pass`; `neutral` and `skipped` are `skipping`; `cancelled` is `cancel`; a run not completed is `pending`; any other conclusion is `fail`.
- **Conclusion.** Computed by the domain, never taken from the caller: FAILED (one failed or was cancelled), else PENDING (one still running), else GREEN when at least one check passed and the others were skipped, NONE when no check passed (no check at all, or only skipped ones: nothing proves the commit, so no merge).
- **A check not created yet is unseen, not absent.** Every check name of the previous evidence of the pull request that is missing from the new read is recorded `name|pending|MISSING`, so the conclusion is PENDING. Branch protection's required checks are not read (not cheap through gh). A check removed on purpose therefore keeps the pull request pending: the director merges on GitHub then.
- **Same repository.** Every read of the checks, of the head and the merge derive the repository from the remote's current URL and compare it with the repository of the pull request's URL: when they differ (the remote was rewritten after the pull request was opened) Floor42 answers 409 `REMOTE_CHANGED` and calls nothing. Known limit: a remote with an explicit port, an `ssh.github.com:443` remote or a repository renamed on GitHub after the pull request opened is refused too (fails closed); the director merges on GitHub.
- **Known limit: the first read.** Only names from earlier evidence are expected. A check that GitHub has not created yet when the first evidence of a pull request is read is unseen: that read can be GREEN with the late check missing. The director's click on a commit and its checks does not close this; branch protection on GitHub does (Floor42 does not read it, see above).
- **Stale.** `GET .../{n}/head` asks GitHub where the branch is and changes nothing. The evidence is stale when the head is another commit than the one recorded. Floor42 does not poll: staleness shows when the director looks, and the merge checks it again whatever the screen said.
- **Merge.** `POST .../{n}/merge {commit}`, the commit being the one whose checks the director read. Refused with 409 before anything is asked of the phone: `EVIDENCE_STALE` (the branch is at another commit, or no evidence), `CHECKS_NOT_GREEN`, `PULL_REQUEST_MERGED`. Then the act is `MERGE` in the assurance table (ADR-0081), level STRONG whether four eyes is on or off (the director asked for one proof, not two people). The route answers 403 `HUMAN_ONLY` to anything but the director's browser session (the cookie), before reading anything: the director's own bearer and script tokens of any scope, IAM mode on or off. In IAM mode a browser follows the step-up (202 `{redirect}`) and the merge is carried out once the signature is recorded, after the same checks again, because the sign-in takes time. With IAM mode off there is no second factor to ask for: the session click is the proof and the approval recorded is `CLICK`, only ever for a cookie.
- **Merge at that commit.** `gh pr merge <n> --repo <r> --squash --match-head-commit <sha>` with the director's own gh (the method is `floor42.gh.merge-method`, `squash` by default): GitHub itself refuses when the branch moved after Floor42's last read. Before anything, a pull request that is not open is refused (409 `PULL_REQUEST_MERGED` for MERGED, `NOT_OPEN` for CLOSED). Afterwards Floor42 asks GitHub for the state and records `PullRequestMerged` only if gh succeeded and the state is `MERGED`. A state still open (auto-merge queued, for instance) or a gh failure with GitHub showing it merged is `GH_FAILED` with the instruction to look on GitHub, nothing recorded. When the state cannot be read after the merge, Floor42 reads it again (`floor42.gh.confirm-attempts` times, 5 by default, `floor42.gh.confirm-delay-millis` apart, 1,000 by default) and then says `MERGE_UNKNOWN`: never "not merged". The merge records the evidence it verified, then merges; reading the checks and merging share one guard per mission (`PULL_REQUEST_RUNNING`), so no other read can change the evidence in between.
- **Journal.** Two new events, Origin REAL, actor the director: `DeliveryEvidenceRecorded(mission, number, commit, checks, conclusion)` and `PullRequestMerged(mission, number, commit, approval)`, where `approval` is `MERGE:pr:<mission>#<n>` (the act whose `ApprovalSigned` rows carry the signer) or `CLICK`. The domain records a merge only if the last evidence is of that commit and GREEN (`EVIDENCE_STALE`, `CHECKS_NOT_GREEN`), once (`PULL_REQUEST_MERGED`). Both appear in the proof dossier (`DELIVERY_EVIDENCE`, `PULL_REQUEST_MERGED`). `PullRequestCheckState` is kept for the journals already written; the screen reads the new event.
- **Where the guard lives.** `IamActGuard` sits in the root of `api` with `AssuranceResponses`, so the delivery context depends on that plumbing and not on the `iam` context.
- **No agent path.** The routes sit under `/api` for the director's session. No MCP tool, no brief, no hook offers them; `ShellGuard` still refuses an agent's `gh`.

## Consequences
- 1.3.1 sets the two rows aside (`NEWER_VERSION`) and shows no merge; checks it recorded with `PullRequestCheckState` still replay. `RollbackEventTypesTest` pins the list.
- A repository with no check cannot be merged from Floor42 (conclusion NONE). The director merges on GitHub, as before.
- More than 100 check runs on one commit is refused, not half read. Paging is the fix when it is seen.
- Squash is the default merge method; a repository that allows only another one sets `floor42.gh.merge-method`.
- The act is STRONG, not FOUR_EYES, on purpose: the pull request was already opened on the director's click and reviewed by the checks. Four eyes can be put on `MERGE` by changing one row of the table.

## Signal to reopen
A merge that carried a commit whose checks were not green, a stale evidence that reached a merge, a repository whose checks are not check runs (statuses only), a commit over 100 runs, or the director asking for the merge to need two people.
